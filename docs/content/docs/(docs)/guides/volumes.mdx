Every app has one volume. It is the writable top of the app's root filesystem: all writes go
there, and it is the only thing that gets backed up. Declare it in `volumes` and point the
instance at it with `volumeId`.

```json
"volumes": [
  { "volumeId": "vol-1", "appId": "app-1", "sizeBytes": 8589934592, "storage": null, "desiredState": "present" }
]
```

## Seeding a volume from an archive

A volume is formatted empty the first time it appears in `desired.json`. To start it with
content, name an archive in the artifact store and where to unpack it:

```json
"volumes": [
  {
    "volumeId": "vol-1", "appId": "app-1", "sizeBytes": 8589934592, "storage": null, "desiredState": "present",
    "initialContents": {
      "digest": "<sha256 of the archive, lowercase hex>",
      "objectKey": "seeds/app-1",
      "destinationPath": "/app/data"
    }
  }
]
```

- The archive is a tar, gzipped or not, or a zip.
- Entries are unpacked under `destinationPath`: `nested/hello.txt` becomes
  `/app/data/nested/hello.txt`. The directory and everything in it are owned by uid 65534.
- Files the archiver added on its own are skipped: `.DS_Store`, `__MACOSX`, `Thumbs.db`, editor
  swap files.
- The volume fails, with the reason in `reported.json`, if an entry escapes `destinationPath`, a
  zip contains a symlink, or the archive does not fit.

<Callout title="Note">
  The archive is unpacked once, when the volume is formatted. Changing or removing
  `initialContents` on an existing volume has no effect.
</Callout>

## Storage backends

`volumes.backend` in `config.toml` selects one of two backends. The
[reference](/docs/reference/config) lists every key of both.

### `local-file`

```toml
[volumes]
backend = "local-file"
storage_prefix = "host-1"
```

Volumes are sparse files under `paths.state_dir`. There is nothing else to configure. A
`[volumes.zerofs]` section on this backend is an error, not ignored. This is the installer's
default.

The limitation: volumes do not survive the machine. Checkpoints and exports are not supported on
this backend, because they are taken in the object store.

### `zerofs`

```toml
[volumes]
backend = "zerofs"
storage_prefix = "host-1"

[volumes.zerofs]
binary = "/opt/nibrunner/bin/zerofs"
config_file = "/etc/zerofs/config.toml"
mount_path = "/mnt/zerofs"
nbd_socket_path = "/run/zerofs/nbd.sock"
ninep_socket_path = "/run/zerofs/9p.sock"
rpc_socket_path = "/run/zerofs/rpc.sock"
storage_url = "s3://my-bucket/host-1"
cache_dir = "/data/zerofs"
cache_disk_gib = 200
cache_memory_gib = 2
checkpoint_runtime_dir = "/run/zerofs-checkpoint"
checkpoint_config_file = "/etc/zerofs/checkpoint.toml"
checkpoint_cache_dir = "/data/zerofs-checkpoint"
```

Volume blocks live in an object store and reach the guest over NBD, through
[ZeroFS](https://github.com/Barre/ZeroFS). `install` generates ZeroFS's configuration files and
systemd units from these keys, so this section is the only place to configure it. The
object-store credentials and the encryption password go in `host.env`.

- **Size `cache_disk_gib` for the disk it is on.** It shares that disk with the snapshots in
  `paths.snapshot_dir`. Losing a snapshot costs one cold boot. Filling the disk breaks the
  filesystem every app on the host runs from.
- **Use whole gibibytes.** The daemon subtracts `cache_memory_gib` from the memory it can promise
  to guests, and reads the value back from the file it generated, which truncates fractions.
- **Slot _N_ uses `/dev/nbdN`.** `install` loads the nbd module with `max_apps + 1` minors. If
  the module is already loaded with fewer, it is not reloaded, because that would detach every
  device under every guest. Raising `max_apps` on this backend therefore needs a reboot.

<Callout type="warn" title="Warning">
  Volumes with `"storage": null` share the host prefix. Deleting that prefix destroys those volumes.
</Callout>

## A customer-owned bucket

On a ZeroFS host, set `storage` when declaring a **new** app volume. Run `nibrunnerd install` and
`nibrunnerd start` after upgrading to install and load the per-app systemd units. Assign one app
and one host exclusive write access to the bucket prefix. Keep the ZeroFS password with the
customer's bucket credentials. Both are needed for independent recovery.

```json
{
  "volumeId": "vol-1", "appId": "app-1", "sizeBytes": 8589934592, "desiredState": "present",
  "storage": {
    "endpoint": "https://objects.example.com", "bucket": "customer-bucket", "prefix": "apps/one",
    "region": "us-east-1",
    "auth": { "kind": "access-key", "accessKeyId": "<access key>", "secretAccessKey": "<secret>" },
    "encryptionPassword": "<customer's ZeroFS password>"
  }
}
```

- The bucket must already exist. Use an HTTPS S3-compatible endpoint supporting the object
  operations and conditional writes required by ZeroFS. Set `region` to the provider's signing
  region, including `"auto"` where supported. `null` uses the writer's `us-east-1` default.
  The host resolves the endpoint for the writer. Its systemd unit denies connections to private,
  loopback, and link-local addresses by default. For a trusted private S3 service, the host
  operator can allow its specific IP with an `IPAddressAllow=` drop-in on that app's writer unit.
- Each app gets a separate writer, NBD client, and cache reservation of 4 GiB disk and 256 MiB
  RAM. Sleeping or omitting the app keeps its writer and placement. An explicit volume deletion
  removes the image, flushes the removal to the bucket, then releases the local cache.
- The host persists the placement across restarts and refuses edits to its bucket or writer
  credentials. Use credentials whose lifetime covers the deployment. Choose a new app and volume
  ID for a different placement. Existing shared disks require a separate data migration.
- S3 credentials and the password reach the host in the desired document. Restrict access to
  that file and the host state directory. The writer has no need for the host's S3 identity.
- The customer prefix contains encrypted ZeroFS objects. Keep the entire prefix, including
  `zerofs.key`. Native host checkpoints and exports currently require host-backed ZeroFS storage.

### Recover the disk independently

Stop the original guest, flush its writer, and stop the original writer before moving ownership.
On a Linux machine with ZeroFS v2.3.1 and `nbd-client`, set `AWS_ACCESS_KEY_ID`,
`AWS_SECRET_ACCESS_KEY` and `VOLUME_PASSWORD` to the customer's values. Create `recovery.toml`
using the original bucket, prefix, endpoint and signing region:

```toml
[storage]
url = "s3://customer-bucket/apps/one"
encryption_password = "${VOLUME_PASSWORD}"

[aws]
endpoint = "https://objects.example.com"
region = "us-east-1"
access_key_id = "${AWS_ACCESS_KEY_ID}"
secret_access_key = "${AWS_SECRET_ACCESS_KEY}"
virtual_hosted_style_request = "false"

[cache]
dir = "/var/tmp/zerofs-recovery"
disk_size_gb = 4.0
memory_size_gb = 0.25

[servers.nbd]
unix_socket = "/run/zerofs-recovery.sock"
```

Start `zerofs run --read-only --config recovery.toml`. In another terminal, attach the export
named after the volume ID to an unused NBD device. Copy it to a new local image and replay its ext4
journal there before reading the files. This example assumes `/dev/nbd0` is free and enough
local disk space is available for the full volume.

```sh
sudo nbd-client -unix /run/zerofs-recovery.sock /dev/nbd0 -N vol-1
sudo dd if=/dev/nbd0 of=recovered.ext4 bs=4M conv=excl,fsync status=progress
sudo nbd-client -d /dev/nbd0
sudo e2fsck -p -E journal_only recovered.ext4
sudo mkdir -p /mnt/recovered-volume
sudo mount -t ext4 -o loop,ro,noload recovered.ext4 /mnt/recovered-volume
ls /mnt/recovered-volume/upper
sudo umount /mnt/recovered-volume
```

## Checkpoints and exports

On the `zerofs` backend, `desired.json` can take a point-in-time copy of a volume and bundle it
as an archive:

```json
"checkpoints": [
  { "checkpointId": "ckpt-1", "volumeId": "vol-1", "desiredState": "present" }
],
"exports": [
  {
    "exportId": "exp-1", "appId": "app-1", "volumeId": "vol-1",
    "format": "tar-gzip",
    "objectKey": "exports/app-1/bundle.tar.gz", "desiredState": "present",
    "environment": { "DATABASE_URL": "sqlite:///app/data.db" }
  }
]
```

- A **checkpoint** is a copy of the volume at the moment it was taken. It stays in the object
  store until `desiredState` is `absent`.
- An **export** freezes the guest's filesystem, takes its own checkpoint, and writes a gzipped
  tar to `objectKey` in `exports.store_url`. The tar holds the volume's contents under `data/`
  and `environment` as `.env`, plus the original `crontab` when the app has registered cron jobs.
  The crontab preserves comments and environment assignments; `.env` and `crontab` have mode
  `0600`. Empty tables and tables containing only comments or environment assignments are omitted.
  To start a new volume from it, point `initialContents` at an
  archive of the `data/` contents, with `destinationPath` `/`.

After restoring the volume, install the exported crontab with `crontab /path/to/crontab` inside
the new deployment.

Each export selects its required `format`: `tar-gzip` or `directory`. For a local consumer
that builds its own bundle, set `"format": "directory"` in that export request. The host publishes
the prepared `data/`, `.env` and `crontab` tree without creating an archive. `objectKey` must be
a single filename, such as `exp-1.export`; the directory is atomically renamed into the local
store, so staging and the store must share a filesystem. A repeated publication of the same key
retains the first completed directory. `sizeBytes` is `null` because no archive was produced.
The consumer owns the published directory's cleanup. A single local store supports both formats;
an S3 store accepts `tar-gzip` only. Unsupported destinations fail before the guest is frozen.

`reported.json` reports the state of each checkpoint and export, with the reason on failure.
