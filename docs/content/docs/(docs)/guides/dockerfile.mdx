---
title: Deploy from a Dockerfile
description: Build a Docker image, package its filesystem, and run it in a microVM.
---

Build your Dockerfile for Linux x86_64, export the image's filesystem, and pack it as a
`filesystem` [layer](/docs/guides/layers). nibrunner boots that layer in a microVM and runs the
command you put in `desired.json`.

Run these commands in one Bash session as root on a Linux nibrunner host with Docker and Buildx,
`squashfs-tools`, and `jq`. The host must be [configured](/docs/getting-started/configuration)
with the default local artifact store and an existing `desired.json`. For a fresh host, use the
[deployment guide's document](/docs/getting-started/deploy-an-app#write-desiredjson) as the starting
point, with this page's volume and instance.

<Steps>
<Step>

## Build the image

Here is a small example that serves a page with Python. Put both files in a new directory:

```html title="index.html"
<h1>Hello from a microVM</h1>
```

```dockerfile title="Dockerfile"
FROM python:3.13-slim-bookworm
WORKDIR /app
COPY --chmod=644 index.html /app/index.html
USER 65534:65534
EXPOSE 8080
CMD ["/usr/local/bin/python3", "-m", "http.server", "8080", "--bind", "0.0.0.0"]
```

Build from that directory. Use your own Dockerfile in its place for an existing app:

```bash
set -euo pipefail
docker buildx build --platform linux/amd64 --load -t docker-demo:build .
docker image inspect docker-demo:build --format '{{json .Config}}' | jq .
```

Keep the inspected configuration: the export in the next step carries files, not the command,
environment, or working directory. Inspection includes defaults inherited from the base image.

</Step>
<Step>

## Pack and upload the filesystem

Use a temporary directory so files left by an earlier export cannot enter the next image:

```bash
work=$(mktemp -d)
container=$(docker create --platform linux/amd64 --entrypoint /bin/true docker-demo:build)
trap 'docker rm -v "$container" >/dev/null; rm -rf "$work"' EXIT
mkdir "$work/rootfs"
docker export "$container" | tar --numeric-owner -xpf - -C "$work/rootfs"
mksquashfs "$work/rootfs" "$work/rootfs.squashfs" -comp zstd -noappend
digest=$(sha256sum "$work/rootfs.squashfs" | cut -d ' ' -f 1)
install -D -m 0644 "$work/rootfs.squashfs" "/var/lib/nibrunner/artifact-store/$digest"
printf '%s\n' "$digest"
```

Keep that digest for both `digest` and `objectKey` below. If you build on a different Linux
machine, copy the squashfs to the host's artifact store under that digest instead. For an object
store, upload it to the store named by `artifacts.store_url` under the same key.

<Callout title="Pack on Linux">
  Root preserves the exported ownership and permissions. Keep extraction and squashfs packaging
  on Linux; copying the extracted tree through a macOS or Windows filesystem can change it.
  [`docker export`](https://docs.docker.com/reference/cli/docker/container/export/) also excludes
  mounted volume contents: it packages the underlying image files, not data from a running app.
</Callout>

</Step>
<Step>

## Describe the app

On the nibrunner host, edit a copy of the desired document:

```bash
cp /var/lib/nibrunner/desired.json /var/lib/nibrunner/desired.next.json
chmod 0600 /var/lib/nibrunner/desired.next.json
```

Keep the existing `hostId` and all other apps, volumes, checkpoints, and exports. Set `revision`
to `docker-demo-1`, add this entry to `volumes`, and choose different ids if these are already in
use:

```json
{
  "volumeId": "docker-demo-vol",
  "appId": "docker-demo",
  "sizeBytes": 1073741824,
  "desiredState": "present"
}
```

Add this entry to `instances`, replacing both digest placeholders with the value printed above:

```json
{
  "appId": "docker-demo",
  "deploymentId": "docker-demo-1",
  "volumeId": "docker-demo-vol",
  "desiredState": "running",
  "layers": [
    {
      "kind": "filesystem",
      "digest": "<sha256 of rootfs.squashfs, lowercase hex>",
      "objectKey": "<same sha256>"
    }
  ],
  "config": {
    "httpPort": 8080,
    "command": {
      "program": "/usr/local/bin/python3",
      "args": ["-m", "http.server", "8080", "--bind", "0.0.0.0"],
      "workingDirectory": "/app",
      "environment": {}
    },
    "resources": { "vcpuCount": 1, "memoryMib": 256 },
    "healthCheck": { "kind": "http", "path": "/", "intervalMs": 5000, "timeoutMs": 2000, "gracePeriodMs": 30000, "healthyThreshold": 1, "unhealthyThreshold": 3 },
    "restartPolicy": { "maxRestarts": 5, "initialBackoffMs": 500, "maxBackoffMs": 30000, "backoffFactor": 2, "resetAfterMs": 60000 },
    "cron": { "maxJobs": 0, "timeZone": "UTC" }
  },
  "hostnames": [{ "hostname": "docker-demo.example.com", "kind": "platform" }]
}
```

The Python example needs no extra environment. For your own image, translate the configuration
shown by `docker image inspect` using the table below. The program must listen on `0.0.0.0`, not
only the guest's loopback address.

Check the edited file against the [desired-state schema](/docs/reference/desired), then replace
the live file. `jq` checks JSON syntax here; it does not validate the schema. Make this edit while
no other tool is writing the desired document:

```bash
jq empty /var/lib/nibrunner/desired.next.json
mv /var/lib/nibrunner/desired.next.json /var/lib/nibrunner/desired.json
```

The rename is atomic because both files are in the same directory. The daemon sees the complete
document and picks it up without a restart.

</Step>
<Step>

## Check the result

Read the report on the host:

```bash
jq '{acceptedRevision, message, instances: [.instances[] | select(.appId == "docker-demo")]}' \
  /var/lib/nibrunner/reported.json
```

`acceptedRevision: "docker-demo-1"` means the document was accepted. Wait for the instance with
`deploymentId: "docker-demo-1"` to report `running`; acceptance alone does not mean the app is
ready. A top-level `message` explains a refused document, and the instance's `message` explains
a failed boot or health check.

```bash
curl --fail -H 'Host: docker-demo.example.com' http://127.0.0.1/
```

The response should contain `Hello from a microVM`. Point your own hostname at the host to reach
it from elsewhere; see [HTTPS](/docs/guides/https) for TLS. App output is in
`/var/lib/nibrunner/logs/docker-demo.log`.

</Step>
</Steps>

## Translate your image's configuration

| Docker image setting | What to put in `desired.json` |
| --- | --- |
| `ENTRYPOINT`, `CMD` | `config.command.program` and `args`. Preserve the effective entrypoint and its arguments, including any wrapper script. Use an absolute program path; resolve names such as `python3` using the image's `PATH`. |
| `WORKDIR` | `config.command.workingDirectory`. Use `/` if the image has none. |
| `ENV` | `config.command.environment`. Include inherited variables the app needs, and supply deployment secrets separately from the image. |
| `EXPOSE` | Select `config.httpPort` explicitly. Other ports use [`config.ports`](/docs/guides/raw-ports); exposing a port does not select a health check. |
| `HEALTHCHECK` | Choose a nibrunner [health check](/docs/guides/health-checks). Docker's command-based check is not imported. |
| `USER` | The guest runs the app as uid/gid 65534. Files must be readable and programs executable by that account; writable data directories must allow it access. |
| `VOLUME` | The app has one persistent writable [volume](/docs/guides/volumes) over its root. Docker volume declarations and host bind mounts are not imported. |

<Callout title="Runtime differences">
  Entrypoints that need root, Docker networking, or host mounts need adapting. The image is a
  layer over nibrunner's Debian base, with the app's writable volume above it. This guide uses
  Python's simple HTTP server to demonstrate packaging; use your application's server for a
  production deployment.
</Callout>

## Redeploy

Build and upload a new squashfs, then replace the existing instance's layer digest and object
key. Change its `deploymentId` and the document's `revision`, and apply the edited document as
above. Keep the existing volume entry and `volumeId` to retain the app's data.

<Callout title="Writes survive a redeploy">
  A file the app wrote into its volume takes precedence over the same path in a new image.
  Keep mutable data separate from packaged application files so an old writable copy does not
  hide an update.
</Callout>
