---
title: Layers
description: How an app's root filesystem is built, and what runs in it.
---

The root filesystem an app sees is a stack. Top to bottom:

```
the volume        writable; the only thing backed up
layers[n-1]
…                 the layers in desired.json, in the order listed
layers[0]
Debian            the guest image nibrunner ships; always the bottom
```

## Layers

A layer names content by its digest, either in the artifact store or in a public OCI registry:

| `kind` | Contents |
| --- | --- |
| `executable` | One program. The host packs it into an image at `destinationPath`. |
| `filesystem` | A squashfs or ext4 image. Attached as uploaded. |
| `oci-registry` | A public registry image pinned to its manifest or index digest. The host selects Linux amd64 and prepares its filesystem. |
| `oci` | A Linux x86_64 OCI image-layout archive. The host verifies its manifests and layers, applies whiteouts, and prepares a read-only filesystem image. |

```json
"layers": [
  { "kind": "filesystem", "digest": "<sha256, lowercase hex>", "objectKey": "base/runtime" },
  { "kind": "executable", "destinationPath": "/app/server", "digest": "<sha256, lowercase hex>", "objectKey": "my-server" }
]
```

A layer is downloaded once per host and cached by digest. Ten apps on the same base image share
one copy.

## The volume

The volume is the writable top of the stack. Every write goes there and persists. Nothing else
persists. An export contains the volume, the environment, and the original crontab when the app
has registered cron jobs, never the contents of a layer. If a layer and the volume both hold a
file at the same path, the volume's copy wins.

## What runs

The guest's init runs `config.command` once the root is assembled: `program` with `args`, in
`workingDirectory`, with `environment`, as uid 65534.

```json
"command": {
  "program": "/app/server",
  "args": ["--port", "3000"],
  "workingDirectory": "/app",
  "environment": { "DATABASE_URL": "sqlite:///app/data.db" }
}
```

If no layer contains the working directory, the host creates it and gives it to uid 65534. The
program can write to the working directory and to `/tmp`. It is chrooted into the stacked root,
so it cannot reach the guest's init, the raw volume, or the host.

## From a Docker image

[Deploy from a Dockerfile](/docs/guides/dockerfile) walks through building an OCI archive and
uploading it as an `oci` layer. The host prepares its filesystem using its existing `mke2fs` and `debugfs` tools;
Docker and squashfs tools are not needed on the host. The image's `ENTRYPOINT`, `CMD`, `ENV`,
`WORKDIR`, `USER`, ports, and health check do not replace the configuration in `desired.json`.

OCI archives must contain one Linux amd64 image in a plain OCI layout tar, with at most 128
layers, 1 GiB of decoded data, 100,000 entries, and 4 MiB of JSON metadata. Device nodes, FIFOs,
sparse files, `LIBARCHIVE` extended attributes, and hard links to symbolic links are refused.
Supported extended attributes use the `SCHILY.xattr.*` tar convention.

## From a public registry

Use `oci-registry` to pull an image directly, without exporting an archive or uploading to the
artifact store. Name the registry and full repository path, plus a lowercase SHA256 digest of
its image manifest or multi-platform index:

```json
"layers": [
  {
    "kind": "oci-registry",
    "repository": "docker.io/library/busybox",
    "digest": "5cec3fc171c87218698e85a52af7087de727372aae264a787b8112901a5b0092"
  }
]
```

This pins Docker's official BusyBox `1.37.0-musl` image. The host selects Linux amd64 from an
index, verifies manifests and blobs, and caches the prepared filesystem by the pinned digest.
A cache hit needs no registry access. Change both the digest and `deploymentId` to deploy another
image version. Image startup defaults still need translating into `config.command`, as described
in [Deploy from a Dockerfile](/docs/guides/dockerfile#translate-your-images-configuration).

Registry access uses HTTPS and anonymous authentication, including public bearer-token challenges.
Private repositories, tags, and insecure HTTP registries are not supported. Registry downloads
are limited to 1 GiB of blobs and use the same filesystem limits as OCI archives above. A registry
outage or rate limit can prevent an uncached deployment; bucket archives remain an alternative.
